# Read Classic · 악보 따라가기

마이크로 연주를 들으면서, 저장해 둔 악보에서 **지금 연주하고 있는 곳**과 **곡이 끝날 때까지 남은 시간**을 실시간으로 보여 주는 웹 앱입니다.
콩쿠르·연주회에서 "이 곡이 언제 끝나는지"를 무대 뒤나 심사석에서 확인하는 용도로 만들었고, 지금은 **피아노**에 맞춰져 있습니다.

- 📷 **사진·PDF·이미지 악보 그대로**: 휴대폰으로 찍은 악보 사진, 악보 PDF, 스캔 이미지를 올리면 악보를 인식해서 저장합니다. MusicXML 도 됩니다.
- 🎹 **원본 악보 위에 위치 표시**: 올린 사진/PDF 위에 지금 줄(옅은 금색 띠), 지금 마디(금색 상자), 지금 음(와인색 막대)을 겹쳐 그립니다.
- ⏱️ **남은 시간·진행률**: "남은 시간 약 2:10", 경과 시간, 진행 %, 남은 마디 수를 크게 보여 주고, 끝나기 N초 전(기본 30초)에 하단이 와인색으로 바뀌며 휴대폰은 진동합니다. 마지막 음이 끝나면 총 연주 시간을 보여 줍니다.
- 📏 **마디·박자로 계산 (기본)**: 음을 하나하나 알아듣는 대신, 악보의 마디·박자표·빠르기 표시로 "악보대로 치면 몇 분짜리 곡인지" 계산하고, 첫 소리가 난 뒤 흐른 시간만큼 위치(마디)를 옮깁니다. 악보 인식이 조금 틀리거나 홀 잔향·페달이 심해도 흔들리지 않고, CPU 도 거의 쓰지 않습니다. **예상 연주 시간**을 넣으면 그 빠르기로 계산합니다. 3초 넘게 조용하면(악장 사이, 연주 중단) 마지막 소리가 난 곳에서 멈췄다가 소리가 다시 나면 이어 가고, 그보다 짧은 쉼표·늘임표는 음악의 일부로 그대로 셉니다. 계산이 연주와 어긋나면 **악보에서 지금 마디를 누르면** 그 자리로 맞추고, 그때까지 걸린 시간으로 빠르기도 다시 잡습니다(도돌이표 반복처럼 멀리 뒤로 누르면 위치만 옮깁니다). 설정 **따라가는 방식**에서 "음을 듣고 따라가기"로 바꾸면 아래의 음 인식 추적을 씁니다.
- 🧭 **시간 검증**: 악보의 빠르기 표시(중간에 바뀌는 것 포함)로 "악보대로면 몇 분짜리 곡인지" 계산하고, 연주 중에는 따라가는 위치가 흐른 시간과 맞게 나아가는지 계속 확인합니다. 소리는 나는데 위치가 멈추거나 엉뚱한 앞 구절로 돌아가면(인식이 틀린 구간 등) "위치 확인 중"으로 바꾸고, 그동안은 흐른 시간으로 위치를 어림해 남은 시간을 계속 줄여 가며 제자리를 다시 찾습니다. 예상 연주 시간보다 크게 빠르거나 느리면 알려 줍니다.
- 🎯 **AI 음 인식 (정밀 추적)**: 마이크 소리를 88건반 하나하나로 알아듣는 AI(Spotify basic-pitch, 브라우저 안에서 실행)를 써서, 음이름 12개만 보던 방식보다 옥타브와 화음 속 각 음까지 구분합니다. 페달·홀 잔향 속 빽빽한 분산화음(바흐 전주곡)에서 음 단위 정확도가 58% → 76%, 마디 91% → 97% 로 올랐습니다. CPU 를 더 쓰고 0.3~0.5초쯤 늦게 따라갑니다. 노트북 앱에서는 기본으로 켜지고, 웹에서는 설정에서 켭니다. 기기가 느려 밀리면 그 부분은 기존 방식으로 따라갑니다.
- ➡️ **지나간 곳으로 돌아가지 않음 (콩쿠르 모드, 기본)**: 위치는 앞으로만 갑니다. 비슷한 앞 구절과 헷갈려 되돌아가는 일이 없습니다. 예외는 둘뿐입니다: 악보에 도돌이표가 있고 연주자가 실제로 반복할 때(구간마다 한 번, 반복을 건너뛰면 그대로 앞으로), 그리고 추적기가 연주자가 칠 수 없을 만큼 앞질러 갔을 때 흐른 시간이 가리키는 곳으로 바로잡는 것. 설정의 **연습 모드**를 켜면 예전처럼 어디로 돌아가 다시 쳐도 따라갑니다.
- 🏛️ **콩쿠르 홀 환경**: 홀 잔향, 오른쪽 페달, 연주 전 박수, 객석 잡음 속에서도 따라가도록 맞췄습니다. 연습 모드에서는 연주자가 앞 구절로 돌아가 다시 쳐도 따라옵니다.
- 🔒 **소리는 브라우저 안에서만** 처리되고 어디에도 보내지 않습니다. (악보 이미지만 인식 서버로 보냅니다.)

## 사용법

1. **악보 넣기** — 왼쪽 목록에서
   - **악보 사진 찍기**: 휴대폰 카메라로 한 쪽씩 찍습니다. (밝은 곳에서, 악보 한 쪽이 화면에 꽉 차게, 똑바로)
   - **악보 파일 추가**: PDF(여러 쪽 가능), 사진·이미지, MusicXML 을 고르거나 끌어다 놓습니다.
   - 사진·PDF 는 "사진·PDF 악보 만들기" 창이 열립니다. 쪽 순서를 확인하고(←/→로 바꾸기) **인식 시작**을 누르면 한 쪽에 10~40초 정도 걸려 인식한 뒤 목록에 저장됩니다. 다음부터는 바로 열립니다.
   - **PDF**: 쪽마다 오선을 찾아 두어, 표지·머리말·해설처럼 **오선이 없는 쪽은 자동으로 뺍니다**(시간 절약, 엉뚱한 음 방지). 쪽 그림을 누르면 넣거나 뺄 수 있고, 여러 곡이 든 PDF 에서 한 곡만 쓰려면 **인식할 쪽**에 `5-12` 처럼 적습니다. 인식이 끝나면 쪽마다 결과가 표시되고(✓ 음표 수 / ⚠ 오선 12개 중 8개 / ✕ 못 읽음), 일부만 읽은 쪽은 저장 뒤 알림으로도 알려 줍니다. 그 부분은 연주할 때 흐른 시간으로 위치를 어림합니다.
   - **여러 파일을 한꺼번에**: PDF 를 여러 개 고르거나 끌어다 놓으면 파일마다 악보 하나씩, 표지·해설 쪽은 빼고 **뒤에서 차례대로** 인식합니다. 목록 위 **인식 중** 칸에서 악보마다 진행 막대·남은 시간을 보고 취소할 수 있고, 끝나면 알림과 함께 목록에 들어갑니다. 그동안 다른 악보를 열어 연습해도 됩니다. 창에서 시작한 하나짜리 인식도 창이 닫히고 뒤에서 진행되며, 끝나면 (연주를 듣는 중이 아니면) 바로 열립니다. 인식 중에 앱 창을 닫으면 멈추므로 닫기 전에 한 번 묻습니다.
   - 둘째 쪽부터는 박자표가 다시 적혀 있지 않으므로 앞 쪽의 박자를 이어받아 마디 길이를 맞춥니다.
2. (권장) **설정 → 예상 연주 시간**에 이 곡을 실제로 치는 길이(예: `6:30`)를 넣어 둡니다. 기본 방식(마디·박자로 계산)은 이 길이로 빠르기를 정하고, 안 넣으면 악보의 빠르기 표시대로 계산합니다(연주 중에 지금 마디를 눌러 맞추면 실제 빠르기로 바뀝니다).
3. **듣기 시작**을 누르고 마이크를 허용합니다. 첫 음이 들리면 계산(따라가기)을 시작합니다. 시작 전 박수는 무시합니다.
4. 연주 중 위치가 어긋나 보이면 악보에서 **지금 치고 있는 마디를 누릅니다.**

| 조작 | 동작 |
| --- | --- |
| 악보 누르기 | 그 음/마디부터 따라가기 (연주 중: 지금 위치로 맞추고 빠르기 다시 잡기) |
| `Space` | 듣기 / 멈춤 |
| `←` `→` | 한 음씩 이동 |
| `Home` | 처음으로 (경과 시간도 처음부터) |
| `−` `+` (위쪽) | 악보 축소 / 확대 |

**설정**(오른쪽 위 아이콘): 따라가는 방식(마디·박자로 계산 / 음을 듣고 따라가기), 예상 연주 시간, 끝나기 전 알림(초), 마이크 감도, 연습 템포, 음정 판정, 악보 인식 서버 주소, 인식된 음 위치 표시(사진 악보에서 인식이 빠진 줄 확인용), 자동 스크롤.

> 마이크는 보안상 **HTTPS** 주소나 `localhost` 에서만 켜집니다.

## 노트북에 설치해서 쓰기 (인터넷 없이)

설치 뒤에는 **인터넷이 없어도** 사진·PDF 악보 인식부터 연주 따라가기, 남은 시간까지 모두 노트북 안에서 됩니다.
웹판(GitHub Pages) 왼쪽 아래의 **노트북용 앱 받기** 버튼이나 아래 링크로 받으세요 (항상 최신판).

| 운영체제 | 받기 | 설치 |
| --- | --- | --- |
| Windows | [ReadClassic-Windows-Setup.exe](https://github.com/saltsongsun/read_classic/releases/latest/download/ReadClassic-Windows-Setup.exe) | 실행 → **설치**. "Windows의 PC 보호"가 나오면 **추가 정보 → 실행**. 바탕화면에 **Read Classic** 아이콘이 생깁니다. |
| Mac (M1 이후) | [ReadClassic-Mac.dmg](https://github.com/saltsongsun/read_classic/releases/latest/download/ReadClassic-Mac.dmg) | 열어서 **Read Classic** 을 **Applications** 로 끌어다 놓기. 처음에 안 열리면 **시스템 설정 → 개인정보 보호 및 보안 → 그래도 열기**. |
| Linux | [ReadClassic-Linux.zip](https://github.com/saltsongsun/read_classic/releases/latest/download/ReadClassic-Linux.zip) | 풀고 `./read-classic` |

- 아이콘을 누르면 브라우저에 앱이 열립니다(`http://localhost:47800`). 창은 따로 뜨지 않고 뒤에서 돕니다.
- 끄기: 앱 오른쪽 위 **설정 → 앱 끄기**. 컴퓨터를 끄면 같이 꺼집니다.
- **업데이트**: 인터넷에 연결돼 있으면 새 버전이 나왔을 때 왼쪽 목록 맨 위에 **새 버전이 나왔어요** 카드가 뜹니다. **지금 업데이트**를 누르면 내려받아 설치하고 1~2분 뒤 새 버전으로 다시 열립니다(저장한 악보는 그대로). 설정 → **앱 버전**에서 직접 확인할 수도 있습니다. 연주를 듣는 중에 저절로 바뀌지는 않습니다.
- 인식한 악보는 그 노트북의 브라우저에 저장됩니다. 문제가 생기면 기록 파일을 봅니다: Windows `%LOCALAPPDATA%\ReadClassic\read-classic.log`, Mac `~/Library/Logs/ReadClassic/`.

설치 파일은 `.github/workflows/desktop.yml` 이 Windows·Mac·Linux 에서 각각 만들고, **실제로 설치해서 인터넷을 막은 채 예제 사진을 인식**해 보고(한글 이름 폴더에서도), **앱 안의 업데이트로 새 판을 설치해 다시 켜지는지**까지 확인한 뒤 `v*` 태그를 올리면 릴리스로 올립니다. 직접 만들려면 `npm ci && npm run build`, `pip install -r desktop/requirements.txt && homr --init`, `python desktop/build.py` (Windows 는 Inno Setup 6 필요) → `desktop/out/`.

## 서버로 실행

사진·PDF 인식에는 **악보 인식 서버**가 필요합니다(오픈소스 OMR 엔진 [homr](https://github.com/liebharc/homr) 사용). 노트북용 묶음에는 이 서버가 들어 있습니다. 직접 띄우는 방법:

```bash
# 1) Docker (권장)
docker build -t read-classic .
docker run -p 8000:8000 read-classic          # → http://localhost:8000

# 2) 직접 (Python 3.11~3.13, Node 22)
npm install && npm run build
pip install -r server/requirements.txt && homr --init   # 인식 모델 약 190MB 내려받기
uvicorn server.app:app --port 8000                       # → http://localhost:8000
```

**휴대폰·태블릿에서 쓰려면** HTTPS 주소가 필요합니다. 위 Docker 이미지를 HTTPS 를 주는 곳(Google Cloud Run, Render, Fly.io 등)에 올리고 그 주소를 휴대폰으로 여는 것이 가장 간단합니다. 웹 앱만 따로(GitHub Pages 등) 올렸다면 **설정 → 악보 인식 서버**에 서버 주소를 넣고, 서버의 `ALLOWED_ORIGINS` 에 웹 앱 주소를 넣어 주세요.

**GitHub Pages**: 저장소 *Settings → Pages → Source* 가 **GitHub Actions** 이면, 기본 브랜치에 올릴 때마다 `.github/workflows/pages.yml` 이 웹 앱을 `https://<사용자>.github.io/<저장소>/` 로 배포합니다. Pages 에는 웹 앱만 올라가므로 MusicXML 악보·예제·마이크 따라가기·남은 시간은 바로 되고, 사진·PDF 인식은 위의 인식 서버 주소를 설정에 넣어야 합니다.

```bash
npm run dev        # 개발 서버 http://localhost:5173 (/api 는 localhost:8000 인식 서버로 넘김)
```

서버 환경 변수: `OMR_TIMEOUT`(한 쪽 제한 시간, 기본 600초), `OMR_CONCURRENCY`(동시 인식 쪽 수, 기본 1), `MAX_UPLOAD_MB`(기본 25), `ALLOWED_ORIGINS`, `HOMR_CMD`.

> homr 는 AGPL-3.0 입니다. 이 앱은 homr 를 별도 프로세스로 실행만 하고 고치지 않습니다. 인터넷에 공개 서비스로 운영한다면 homr 저장소 링크를 안내해 주세요.

## 동작 원리

```
사진/PDF ─▶ 쪽별 이미지 ─▶ 인식 서버(homr) ─▶ MusicXML + 줄 위치 ─▶ 악보 이벤트 + 원본 위 좌표
마이크 ─▶ AudioWorklet ─▶ 특징 추출 ─────────────────────────────▶ 악보 추적기(HMM) ─▶ 위치 · 남은 시간
             · 크로마(12음 이름) · 새로 생긴 소리의 크로마
             · 온셋(새 음 시작)   · 레벨·스펙트럼 평탄도(잡음/박수)
```

1. **사진/PDF → 악보** (`server/app.py`, `src/score/importImages.ts`, `src/score/musicxml.ts`, `src/score/imageLayout.ts`)
   PDF 는 브라우저에서 pdf.js 로 쪽별 이미지로 바꾸고, 사진은 방향을 바로잡아 서버로 보냅니다. 서버는 homr 로 MusicXML 과 줄(큰보표)마다의 위치를 돌려줍니다.
   앱은 MusicXML 을 직접 읽어(붙임줄·화음·여러 성부·꾸밈음 처리) 음 이벤트를 만들고, 줄바꿈 표시로 마디를 줄에 배정해 원본 이미지 위 좌표를 계산합니다.
   (homr 새 버전이 음표마다 넣어 주는 `<!-- imgpos -->` 좌표가 있으면 그걸 씁니다.)
2. **소리 → 특징** (`src/audio/features.ts`): 약 85ms 창 FFT 의 스펙트럼 봉우리로 크로마를 만들고, 직전보다 커진 성분만 모은 "새로 생긴 소리" 크로마, 짧은 창의 스펙트럴 플럭스 온셋(평균 기준 + 바닥값 기준을 함께 써서 잔향 속 빠른 음도 잡음), 레벨과 평탄도로 잡음·박수를 걸러 냅니다.
3. **추적** (`src/follow/tracker.ts`): 음 이벤트마다 *어택*·*지속* 상태를 둔 은닉 마르코프 모델입니다.
   - 지속 상태는 "마른 소리" 템플릿과 "앞 음들이 울리는(페달·잔향)" 템플릿 중 잘 맞는 쪽을 써서 방 소리에 스스로 맞춥니다.
   - 머문 시간 ÷ 예상 길이(템포 × 박)로 다음 음 확률이 커지고, 늘임표처럼 오래 끌면 기다립니다. 템포는 계속 보정합니다.
   - 틀린 음은 유사도 하한으로 영향을 제한하고, 최근 2초를 다시 풀어 보는 재탐색으로 되돌아가 다시 치는 것을 잡습니다. 콩쿠르용으로 앞으로 건너뛰기는 매우 엄격하게, 두 번 연속 같은 결론일 때만 옮기며, 마지막 음 이후(박수)에는 위치를 바꾸지 않습니다.
4. **남은 시간** (`src/follow/progress.ts`): 음마다 "악보 빠르기대로 치면 걸리는 시간"(명목 시간, 빠르기 바뀜 반영)을 매기고, 남은 명목 시간 × 속도 비율(실제 ÷ 명목)로 계산합니다. 속도 비율은 사전값(예상 연주 시간 > 악보 빠르기 > 어림)과 지금까지 실제로 걸린 비율을 각자 믿을 만한 정도에 따라 섞습니다.
5. **AI 음 인식** (`src/audio/keyModel.ts`, `keyWorker.ts`): 마이크 소리를 22050Hz 로 바꿔 0.25초마다 최근 2초를 basic-pitch 모델(ONNX, onnxruntime-web, 웹 워커)에 넣고, 88건반의 "울리는 음"·"방금 친 음" 확률을 받습니다. 추적기는 이 확률을 악보 이벤트의 88건반 템플릿(새 음 + 이어지는 음 + 페달로 남은 앞 음)과 비교해 크로마 유사도와 반반 섞습니다(옥타브를 잘못 읽은 사진 악보도 크로마로 어느 정도 맞춥니다). 결과가 나온 시각까지의 소리만 처리하므로 그만큼 늦게 따라가고, 너무 밀리면 그 프레임은 AI 없이 처리합니다.
6. **시간 검증** (`src/follow/progress.ts`): 0.25초마다 최근 8초 동안 위치가 믿던 속도만큼 나아갔는지 봅니다. 소리가 계속 나는데 30%도 못 나아갔거나 뒤로 갔으면 "놓침"으로 보고, 마지막으로 믿을 수 있던 지점부터 시간으로 위치를 어림합니다. 이 어림 위치를 추적기의 재탐색에 힌트로 줘서 그 주변도 찾게 하고, 위치가 어림 근처에서 다시 고르게 나아가면 돌아옵니다. 바흐 전주곡에서 40개 음을 일부러 틀리게 바꾼 악보로 시험하면, 예전에는 추적이 끝까지 길을 잃고 남은 시간이 최대 8분까지 틀렸지만 지금은 그 구간 뒤에서 98% 제자리를 찾고, 놓친 동안에도 남은 시간 오차가 곡 길이의 20% 이내입니다(`tests/progress.test.ts`).
7. **마디·박자로 계산 (기본 방식)** (`src/follow/beatClock.ts`): 음마다 "악보 빠르기대로 치면 걸리는 시간"(박 수 × 60 ÷ 빠르기, 중간에 바뀌는 빠르기 반영)을 쌓아 곡 전체 길이를 내고, 속도 비율(예상 연주 시간 ÷ 악보 길이, 없으면 1)을 곱해 실제 길이로 바꿉니다. 마이크는 "소리가 나는지"만 봅니다. 첫 소리부터 흐른 시간(3초 넘는 침묵은 빼고) ÷ 속도 비율이 지금까지 연주한 악보상 시간이고, 그 시점의 음·마디가 지금 위치입니다. 사용자가 짚은 위치가 계산 위치 근처면(어긋남 보정) 지금까지 걸린 시간 ÷ 그동안 연주한 악보상 시간(반복한 구간 포함)으로 속도 비율을 다시 잡습니다.

## 정확도

### 사진 악보 인식 (실제 homr 0.7.0)
예제 악보를 이미지로 그린 것과, 그것을 휴대폰 사진처럼 기울이고 그늘·잡음·JPEG 압축을 넣은 것을 실제로 인식했습니다(`tests/omr/`). 이 인식 결과로, 정답 악보로 합성한 피아노 연주(홀 잔향 + 페달)를 따라갔습니다(`tests/omr-quality.test.ts`).

| 악보 | 인식 시간 (CPU) | 음높이 일치 | 마디 ±1 이내 | 마지막 마디 도달 |
| --- | --- | --- | --- | --- |
| 환희의 송가, 깨끗한 이미지 | 11초 | 100% | 100% | ✓ |
| 환희의 송가, 사진 흉내 | 10초 | 100% | 100% | ✓ |
| 바흐 전주곡 C장조 19마디 (큰보표), 깨끗한 이미지 | 29초 | 93.4% | 87.4% | ✓ |
| 같은 곡, 사진 흉내 | 28초 | 91.4% | 87.4% | ✓ |

### PDF 악보 인식 (`sh tests/pdf-bench/run.sh`)
정답을 아는 예제 악보로 실제 악보집처럼 빽빽한 A4 PDF(표지·머리말 쪽 포함)를 만들고, 같은 쪽을 스캔본처럼 기울이고 흐리게 하고 잡음을 넣어 흑백으로 만든 PDF 도 만들어, 앱과 같은 방식으로 쪽 그림으로 바꿔 인식했습니다.

| PDF | 표지·머리말 | 음높이 일치 (바흐·환희의 송가·작은 별 평균) | 마디 ±1 따라가기 |
| --- | --- | --- | --- |
| 악보 프로그램에서 만든 PDF | 자동으로 뺌 | 96.2% | 99.1% |
| 300dpi 흑백 스캔 (기울어짐·잡음) | 자동으로 뺌 | 96.2% | 99.1% |
| 150dpi 흑백 스캔 (오선이 점선처럼 끊김) | — | 6% | 37% |

300dpi 정도로 스캔한 PDF 는 깨끗한 PDF 만큼 읽습니다. 오선이 끊길 만큼 거친 저해상도 스캔은 인식 엔진이 오선을 찾지 못해 읽지 못합니다(기울기 보정·오선 잇기 전처리도 시험했지만 나아지지 않았습니다). 이런 PDF 는 다시 스캔하거나(300dpi 이상), 휴대폰으로 종이 악보를 찍는 편이 낫습니다. 인식 엔진은 켜 둔 채 쪽마다 일을 넘겨서, 쪽마다 새로 켜던 때보다 10% 남짓 빠릅니다.

피아노처럼 성부가 여럿인 악보는 음높이는 대부분 맞게 읽지만 박 위치(쉼표·붙임줄·성부 정렬)가 어긋나는 일이 많습니다. 그래서 사진 악보는 음 하나하나보다 **마디 단위**로 보는 것이 정확합니다.

### 브라우저 종단 시험 (`npm run e2e`)
Chromium 의 가짜 마이크로 합성 연주를 넣고 실제 앱을 조작했습니다. 사진 악보는 사진 업로드 → 인식 서버(실제 homr) → 따라가기까지 거칩니다.

| 시험 | 결과 |
| --- | --- |
| 환희의 송가 (MusicXML) | ±1음 100%, 마지막 음까지 |
| 바흐 전주곡 (MusicXML) | ±1음 100%, 마지막 음까지 |
| 환희의 송가, 마디·박자로 계산 (예상 연주 시간만 넣고, 악보 빠르기의 90% 에 ±8% 흔들림) | 마디 ±1 99.6%, 남은 시간 오차 0%, 마지막 마디·연주 끝 인식 |
| 바흐 전주곡, 마디·박자로 계산 (같은 조건) | 마디 ±1 99.9%, 남은 시간 오차 0%, 마지막 마디·연주 끝 인식 |
| 환희의 송가 (사진 → 인식) | 마디 ±1 100%, 남은 시간 오차 곡 길이의 0~1% (50%·75% 지점), "곧 끝나요"가 끝나기 10초 전 무렵에만 표시, 연주 끝 인식 |

### 합성 연주 추적 (`npm run report`)
"±1음"은 소리가 나는 동안 커서가 실제 위치에서 한 음 이내였던 비율, "마디"는 마디가 맞은 비율입니다.

| 상황 (피아노) | ±1음 | 마디 |
| --- | --- | --- |
| 환희의 송가·작은 별, 악보 템포의 0.55~1.35배 | 100% | 98.6~99.3% |
| 바흐 전주곡 C장조 (분산화음 304개 지점), 마른 소리 | 100% | 99.4% |
| 　〃 오른쪽 페달 | 98.2% | 99.1% |
| 　〃 홀 잔향 | 78.7% | 96.6% |
| 　〃 페달 + 홀 잔향 | 69.2% | 95.5% |
| 환희의 송가, 페달 + 홀 잔향 | 99.3% | 98.8% |
| 환희의 송가, 느리게 + 페달 + 강한 홀 잔향 | 93.4% | 91.5% |
| 4초 박수 뒤 시작 | 100% | 97.7% |
| 3초 멈췄다 다시 | 99.9% | 99.1% |
| 틀린 음 10% 섞어 치기 | 99.1% | 97.4% |
| 10마디까지 치다가 9마디로 돌아가기 | 91.3% | 90.4% |

모든 경우 마지막 음까지 따라갔습니다. 홀 잔향 속 빠른 분산화음처럼 음 하나하나가 뭉개지는 곳에서도 마디는 95% 이상 맞습니다. 남은 시간 추정은 곡 중반 이후 실제와 곡 길이의 2% 이내였습니다(시험 기준은 8%, `tests/follower.test.ts`).

### 한계
- 사진은 밝고 반듯할수록 잘 읽힙니다. 손글씨 악보, 심하게 구겨진 종이, 8va 줄·옥타브 음자리표 등 homr 가 아직 읽지 못하는 기호가 많은 악보는 인식이 틀릴 수 있습니다. 설정의 **인식된 음 표시**로 빠진 줄이 없는지 확인할 수 있습니다.
- 현재 PyPI 판 homr(0.7.0)는 음표별 좌표를 주지 않아서, 마디의 가로 위치는 줄 안에서 마디 길이 비율로 나눈 근삿값입니다(줄 위치는 정확).
- 마디·박자 방식은 연주자가 악보 빠르기(또는 예상 연주 시간)에서 크게 벗어나 치거나 rubato 가 심하면 그만큼 위치가 어긋납니다. 이때는 지금 마디를 눌러 맞추거나 "음을 듣고 따라가기"로 바꿉니다. 도돌이표 반복은 계산에 넣지 않으므로, 반복하는 곡은 예상 연주 시간을 넣거나 반복할 때 돌아간 마디를 눌러 줍니다.
- 도돌이표는 펼치지 않습니다. 반복을 하면 "앞 구절로 돌아가 다시 치기"로 따라가는데, 알아채는 데 1~3초 걸립니다.
- 똑같은 선율이 여러 번 나오는 곡에서 처음부터 다시 치면, 두 구간이 달라지는 곳까지는 다른 반복 구간에 붙어 있을 수 있습니다.
- 크로마(음 이름) 기반이라 옥타브만 다르게 친 것은 구분하지 못합니다. 피아노 외 악기와 여러 악기 합주는 아직 맞추지 않았습니다.
- 인식된 악보는 그 브라우저에만 저장됩니다. 다른 기기에서 쓰려면 그 기기에서 다시 올려야 합니다.

## 개발

```bash
npm test             # 단위·추적·실제 인식 결과 추적 시험 (약 1분)
npm run typecheck
npm run report       # 상황별 정확도 표
npm run e2e          # Chromium 가짜 마이크 종단 시험 (Playwright 필요; 인식 서버가 없으면 저장된 실제 인식 결과로 대신)
python -m pytest server/tests   # 서버 시험 (fastapi, httpx, pytest 필요)
```

```
server/app.py            악보 인식 서버 (homr 실행, 웹 앱 제공)
src/audio/               마이크 입력, FFT, 크로마·온셋·잡음 판별
src/follow/tracker.ts    악보 추적기 (HMM + 재탐색)
src/follow/progress.ts   진행률·남은 시간
src/score/musicxml.ts    MusicXML 해석 (homr 결과 포함)
src/score/imageLayout.ts 원본 악보 위 좌표 계산
src/score/imageView.ts   원본(사진/PDF) 악보 화면
src/score/importImages.ts 사진·PDF → 쪽 이미지, 인식 서버 호출
src/score/view.ts        MusicXML 악보 화면 (OpenSheetMusicDisplay)
src/score/library.ts     브라우저(IndexedDB) 악보 보관함
tests/                   합성기·시나리오·시험, tests/omr/ 실제 인식 결과
```

예제 악보는 모두 저작권이 만료된 곡을 직접 입력한 것입니다.
